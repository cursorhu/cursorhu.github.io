10BASE-T1S 碰撞窗口深度分析：为什么 CSMA/CD 同步触发无法产生 collision

cursorhu
2026-09-11
Ethernet › 嵌入式网络 › 协议分析
10BASE-T1S, CSMA/CD, LAN8650, PLCA, 碰撞检测

引言

在调试 LAN8650 双板碰撞测试时，遇到一个反直觉的现象：两个板子通过 GPIO 同步触发 TX，却始终观测不到 CORTXCNT 自增和 TXCOL 置位。本文从 IEEE 802.3 协议规定、PHY 物理层行为、MAC 状态机调度三个层面逐步分析原因，并给出唯一能可靠触发碰撞的方案。

一、标准 CSMA/CD 碰撞窗口是固定的 51.2μs

1.1 IEEE 802.3 的硬性规定

10BASE-T1S（Clause 147）沿用 10BASE-T 的 slot time 定义：

这个值不可配置、不可扩展。其物理意义是：最远两端之间的往返传播延迟必须 ≤ 25.6μs（slot time 的一半），否则后开始 TX 的站点可能在已停止 TX 后才”收到”碰撞信号，碰撞丢失。

1.2 10BASE-T1S 的物理条件

10BASE-T1S 多分支段最长 25m，传播速度 5ns/m：

物理碰撞窗口其实只需要 250ns，但 MAC 层仍按 51.2μs 处理以保持兼容。

1.3 PHY 层 collision detection 是连续的

datasheet §7.2.5（LAN8650/1 Data Sheet DS60001734F）：

“when the PHY detects a collision while transmitting the Transmit Collision Status (TXCOL) bit is set”

TXCOL 和 CORTXCNT 监测整个 TX 期间，不限于开头 51.2μs。

2.3 关键因果链

问题根源：两板几乎同时完成 endPacket()，但不会同时进入 TC6_Service()。SPI 访问、lwIP 调度差异导致两板错开 100us 到数 ms。

2.4 Carrier Sense 推迟机制

时间顺序 板 A 板 B
T=0 D3 拉低 D3 拉低
T=2us ISR 退出 ISR 退出
T=500us endPacket() 完成 endPacket() 完成
T=520us TC6_Service() 进入，读 CRS 等待中
T=520us CRS=0（都还空闲）→ 启动 TX 等待中
T=530us TX 在 MDI 上，CRS=1 TC6_Service() 进入，读 CRS
T=530us TX 进行中 CRS=1 → 等待
T=2500us TX 结束，CRS=0 等待中
T=2500us - CRS=0 → 启动 TX
T=2501us - TX 在 MDI 上

结果：

  • 板 A: carrier wait ≈ 0，TX OK，无 collision
  • 板 B: carrier wait ≈ 2500us（一个帧时间），TX OK，无 collision

2.5 Carrier Wait 数值证据

来自三次实验：

触发 Carrier Wait 含义
#1 2510 us 对端刚完成一个帧 TX
#2 2364 us 同上
#3 6916 us 对端连续 TX 多次

所有 Carrier Wait 都不是 0，说明 carrier sense 一直在工作，两板 TX 永远不会在 MDI 上重叠。

2.6 即使 ISR 完美同步也无法解决

要让两板在 MDI 物理层同时出现信号：

  1. 两板 MAC 状态机同时认为总线空闲
  2. 两板同时启动 TX（PHY TX_EN 同时拉高）

这两条要求 CSMA/CD 永远不满足——CSMA/CD 的设计目标就是避免两者同时 TX。

三、唯一能可靠触发碰撞的方法：PLCA 同 NodeID

3.1 PLCA 的 TO 时隙机制

PLCA（Physical Layer Collision Avoidance）用 NodeID 分配 TO：

关键：TO 由 NodeID 决定，不依赖 carrier sense。

3.2 同 NodeID 必然碰撞

两板都配 NodeID=0：

  • 都在 TO=0 启动 TX
  • 没有 carrier sense 推迟
  • 双方在 PHY 层同时驱动 MDI → 必然 wire-level collision

datasheet §7.2.4：

“should a collision be detected while the device is transmitting in its assigned transmit opportunity, the Transmit Collision (TXCOL) status bit will be set”

3.3 libtc6 在 PLCA 模式下仍使能 collision detection

模式 CDCTL0 CDEN CDBM TXCOL 行为
CSMA/CD 0x8083 1 1 retry 自动清除
PLCA 0x0083 1 0 锁定直到读取

两种模式 CDEN=1，collision detection 硬件始终使能。

四、验证方案对比

方案 NodeID 配置 CORTXCNT TXCOL 说明
A: Control (CSMA/CD) (0, 0) 0 0 CSMA/CD 推迟工作正常
B: Exp (CSMA/CD) (0, 1) 0 0 不同节点
C: Forced Coll (PLCA) (0, 0) ≥1 1 同 TO，PHY 必检测
D: No Coll (PLCA) (0, 1) 0 0 不同 TO

方案 A/B 的”无 collision”现象不是 bug，是协议设计目标。

已知风险

两板都是 NodeID=0 → 都是 coordinator → 都发 BEACON → BEACON 互相干扰。

后果：PLCA sync 不稳定。但一旦 sync 成功，同 TO 的碰撞必然发生。

结论

  1. CSMA/CD 碰撞窗口 51.2μs 是 IEEE 802.3 强制规定，不可扩展。
  2. CSMA/CD 双板 D3 同步触发无法产生 collision 不是 bug，是协议设计目标。Carrier wait > 0 是 carrier sense 工作的直接证据。
  3. PHY 碰撞检测在整个 TX 期间持续工作，但只有 MDI 信号实际损坏时才计数。
  4. PLCA 同 NodeID 是唯一能可靠触发碰撞的方案，datasheet §7.2.4 保证 TXCOL 必置位。
